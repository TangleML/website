# Managing Secrets

Secrets let you pass credentials, API keys, and other sensitive values to pipeline components without embedding them in your pipeline YAML or argument fields.

Secret values are stored securely on the TangleML backend and referenced by name at runtime. The value is never stored in the browser or in the pipeline definition — only the secret name is.

## Managing secrets

Navigate to **Settings → Secrets** to view and manage your secrets. The **Secrets Management** page lists each secret by name, with its description if it has one and when it was added.

### Adding a secret

1. Click **Add Secret**.
2. Enter a **Secret Name**. This name is used to reference the secret in component arguments. It cannot contain `/` or be `.` or `..`, and it can be up to 255 characters long.
3. Enter the **Secret Value**. It is masked as you type and is never displayed again.
4. Optionally, add a **Description** of what the secret is for, up to 255 characters, and an **Expires** date picked from a calendar.
5. Click **Add Secret**.

:::info
An expiry date records when the secret is due to be rotated. The open-source TangleML backend stores the date but does not act on it, so the secret keeps working after the date passes.
:::

### Replacing a secret

Secret values cannot be read back from the backend after they are saved. To update a secret's value:

1. Find the secret in the list and click its pencil button. The **Replace Secret** page opens with the name filled in. The name cannot be changed.
2. Enter the **New Secret Value**.
3. Optionally, change the description or the expiry date. A description can be changed but not removed. If the secret already has an expiry date, the hint under **Expires** shows it, and leaving the field empty keeps it.
4. Click **Update Secret**.

### Deleting a secret

Click the trash button next to a secret. A **Delete "&lt;name&gt;"?** dialog warns that runs that use the secret will fail when they start. Click **Delete** to remove it permanently.

:::warning
Deleting a secret that is referenced in a pipeline argument will cause that argument to fail at execution time. Update any pipelines that reference the secret before deleting it.
:::

## Using secrets in component arguments

When configuring a task input in the [pipeline editor](/docs/user-guide/pipeline-editor#arguments), open the lightning-bolt menu next to the argument and choose **Dynamic Data** to switch from a static value to a dynamic source. It offers two kinds of value:

- **Secrets**: **Select Secret...** opens the **Select a Secret** dialog, which lists your secrets. Click one to bind the argument to that secret's value. At execution time, the backend injects the actual value — it is not visible in the editor or the pipeline YAML. **Add Secret** in the dialog opens the same form as **Settings → Secrets**, then returns you to the list.
- **System data**: Runtime-provided values such as the pipeline run ID, pipeline name, and current timestamp. Useful for generating unique output paths or annotating runs without hardcoding values.

The argument field displays the secret or system data name rather than its value. The resolved value is only available to the executing component at runtime.

## Secrets in a run

A secret's value is resolved when the task launches and is never saved as an artifact. In the [run view](/docs/user-guide/run-view#task-inspection), an input bound to a secret shows a lock and the secret's name, both on the canvas and in the task's **Artifacts** tab. The value itself is not shown anywhere in the run.

:::tip
System data arguments are particularly useful for outputting artifacts to unique per-run paths, for example: combining the run ID with a fixed prefix to avoid collisions across multiple runs of the same pipeline.
:::
