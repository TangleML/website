The Published Components Library enables teams to share, discover, and maintain reusable components across workspaces. This guide walks you through the essential workflows for publishing, discovering, and maintaining components.

## Overview

The Published Components Library provides a centralized repository where teams can:

- **Share** tested and documented components
- **Discover** components created by team members
- **Maintain** component versions with seamless upgrades
- **Ensure quality** through validation checks

:::tip
Published components are shared across your entire workspace, making it easy for teams to collaborate and reuse proven solutions.
:::

## Publishing Components

Transform your local Components into reusable workspace assets through the publishing workflow.

### Steps to publish

1. Add your component to your user library — for example by dropping its YAML onto the editor canvas — then configure and test it in a pipeline.
2. In the **Component Search** window, clear the search box, open the **User Components** folder, and click the component's ⓘ button to open its details dialog.
3. Open the **Publish** tab. It appears only for your own user components. It shows a **Component Review** of the author, name, description, digest, and publisher, and the component's **Publish History**.
4. Click **Publish component**. The confirmation dialog includes a **ComponentSpec quality check** of the component's name and description, and the type and description of each input and output. The check is advisory: fixing what it flags makes the component easier to use, but is not required to publish.
5. Click **Continue**. **Component published successfully** confirms that your component is now available to all workspace users.

:::warning
Once published, components cannot be deleted to ensure pipeline stability. Instead, publish new versions to update functionality.
:::

### Best practices for publishing

| Practice                   | Description                                                            |
| -------------------------- | ---------------------------------------------------------------------- |
| **Complete documentation** | Include clear descriptions, parameter explanations, and usage examples |
| **Semantic naming**        | Use descriptive names that clearly indicate the component's purpose    |
| **Version tags**           | Add meaningful tags to help users understand version changes           |
| **Test thoroughly**        | Validate your component in different scenarios before publishing       |

## Discovering Components

Find and integrate published Components quickly using the search and discovery features.

### Search and add components

1. **Search in the Component Search window**
   - Type keywords in the search box. Published components show **Published by** and the publisher's name.
   - Narrow the results to published components with the source filters, or browse the **Published Components** folder with the search box empty.
   - The search matches names and descriptions, and the component's `author` annotation, but not the publisher's user name.

2. **Drag to canvas**
   - Select your desired component from search results
   - Drag it directly onto the pipeline editor canvas
   - Configure parameters as needed

See [Component Search](/docs/user-guide/component-search) for more on searching.

:::tip
Use descriptive search terms like "data preprocessing" or "model training" to find relevant components faster.
:::

## Releasing new versions

Keep your published Components up-to-date with the versioning workflow.

### Update process

1. **Load the updated component**
   - Add the new version to your user library under the same name, by dropping its YAML onto the canvas or saving it from the [in-app editor](/docs/component-development/in-app-editor)
   - Make necessary modifications and improvements

2. **Open the component**
   - In the **Component Search** window, open **User Components** and click the component's ⓘ button
   - Open the **Publish** tab. Its history notes that you have a version of the component that is not published yet

3. **Release the new version**
   - Click **Release new version** and confirm with **Continue**
   - **Component updated successfully** confirms the release, and the previous version is marked deprecated

**Release new version** is offered only when the component keeps the same name, you published the previous version, and that version is not already deprecated. There is no field for version notes, so describe what changed in the component's own description or annotations.

:::warning
Breaking changes should be clearly documented in the component's description to help users migrate smoothly.
:::

## Receiving component upgrades

When a newer version of a published component exists, tasks that use an older one are marked on the canvas with an orange book icon, beside the task's short digest. The same icon marks the component in the **Component Search** browse view.

To upgrade a task, drag the newer version from **Component Search** onto it, and confirm the **Replace Task?** dialog with **Continue**. The dialog shows which inputs and outputs the new version adds, keeps, or removes before anything changes. You can use different component versions for different tasks in the same pipeline.

:::info
If you turn **Component Search** off under **Settings → Beta Features**, the editor shows the older **Components** window instead. That window shows an **Upgrades available** alert when tasks can be upgraded. **Review** opens an **Upgrade Components** window listing them, with a checkbox for each task and an **Upgrade** button. **Dismiss** hides the alert for 24 hours.
:::

## Best practices

### For publishers

- **Document thoroughly**: Include examples and edge cases
- **Version responsibly**: Use semantic versioning
- **Communicate changes**: Write clear release notes
- **Maintain backward compatibility**: When possible

### For consumers

- **Review before updating**: Check release notes and breaking changes
- **Test in development**: Validate updates before production
- **Pin versions**: For critical pipelines that need stability
- **Report issues**: Help improve components by providing feedback

## Troubleshooting


| Issue                                 | Solution                                           |
| ------------------------------------- | -------------------------------------------------- |
| **Validation fails during publish**   | Review documentation and required fields           |
| **Component not appearing in search** | Wait a few moments for indexing, refresh page      |
| **Conflicts during update**           | Review parameter mappings and adjust manually      |

:::warning
Always backup your pipeline configuration before applying major component updates, especially in production environments.
:::
